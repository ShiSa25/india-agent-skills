# Sources

Rules as of 2026-11-01. A bullet is either a page that was opened or an explicit UNVERIFIED tag.

- [Validate and test webhooks](https://razorpay.com/docs/webhooks/validate-test/) — opened 2026-11-01. `X-Razorpay-Signature` is HMAC-SHA256 hex of the raw body with the webhook secret. Do not parse or cast the body. Idempotency header `x-razorpay-event-id`. Events can arrive out of order (`payment.authorized` then `payment.captured` is the ideal order and is not guaranteed). The Node sample on this page calls `JSON.stringify(webhookBody)`; this skill does not, because that re-serialises a parsed value and the same page forbids parsing.
- [Webhook best practices](https://razorpay.com/docs/webhooks/best-practices) — opened 2026-11-01. Non-2xx responses retry on exponential backoff for 24 hours. A handler that misses the 5 second response is treated as a timeout and retried.
- [Set up payments webhooks](https://razorpay.com/docs/webhooks/setup-edit-payments) — opened 2026-11-01. Return a 2xx within 5 seconds or the delivery is a failure.
- [Payments webhook events](https://razorpay.com/docs/webhooks/payments) — opened 2026-11-01. `payment.authorized`, `payment.captured`, `payment.failed`. `order.paid` fires when the order becomes paid. A captured payment can still be followed by a late `payment.authorized` snapshot. `payment.failed` then `payment.captured` happens on UPI retries.
- [Payment capture settings](https://razorpay.com/docs/payments/payments/capture-settings) — opened 2026-11-01. Authorised payments must be captured within 3 days or they are auto-refunded. Auto and manual capture timeouts: minimum 12 minutes, default and maximum 3 days. Direct settlement merchants are auto-captured. Normal auto-refund speed is 5 to 7 working days.
- [Refund webhook events](https://razorpay.com/docs/webhooks/refunds) — opened 2026-11-01. `refund.created`, `refund.processed`, `refund.failed`. Auto-refunds of uncaptured payments have `payload.payment.entity.captured` false. The published `refund.created` sample body shows `status` `processed`; the ledger still moves only on `refund.processed`.
- [Create an order](https://razorpay.com/docs/api/orders/create) — opened 2026-11-01. Amount is an integer of subunits. INR error text: "The amount must be at least INR 1.00". The solution line says greater than or equal to 100. The same accordion also says "greater than 100"; this skill accepts 100. Three-decimal amounts must end in subunit 0: 295.991 is sent as 295990 and 99.991 as 99990. JPY 295 is sent as 295. The maximum is the limit configured for the account, not a single published cap.
- [Standard checkout integration](https://razorpay.com/docs/developer-tools/integrations/standard-checkout) — opened 2026-11-01. Checkout signature is HMAC-SHA256 of `order_id|payment_id` with the key secret. Retrieve `order_id` from your server. Currency minima on that page: INR 100, USD 50, EUR 50, GBP 30, SGD 50. Fulfil on captured. The page also shows a ₹5,00,000 example maximum; the orders API describes the maximum as account-specific, so this skill does not enforce ₹5,00,000.
- [Checkout signature step](https://razorpay.com/docs/build/llm-docs/payments/payment-gateway/web-integration/custom/build-integration.md) — opened 2026-11-01. Same HMAC construction. Sample ids `order_9A33XWu170gUtm` and `pay_29QQoUBi66xm2f` are used as fixtures. The published signature on that page has no published secret, so tests compute HMAC with `node:crypto` and a test secret.
- [International currency exponents](https://razorpay.com/docs/build/llm-docs/payments/international-payments.md) — opened 2026-11-01. Exponent table used for subunits. That page's example of 99.999 KWD as 99999 contradicts the orders API trailing-zero rule. This skill follows the orders API.
- [Razorpay MCP server](https://razorpay.com/docs/mcp-server) — opened 2026-11-01. Create orders, capture, and refund through this server. Remote endpoint `https://mcp.razorpay.com/mcp`. The SSE URL `https://mcp.razorpay.com/sse` is deprecated from 13 Aug 2025.
